## 1. 建设目标与范围

平台应形成“数据采集接入 → 数据治理 → 人工标注与自动保存 → 数据版本冻结 → 训练 → 独立评估 → 机器人部署交付 → 难例回流”的闭环。网站可运行是原型成果；正式目标是持续产出标签可追溯、结果可复现、可在指定机器人硬件上运行的视觉模型。用户已确定四人使用；按其当前意见，首期默认不设标注提交和专家复核流程。

**本轮范围校正**：提供的机器人方案以按钮检测和 RGB-D 定位为 P0，属于机器人操作视觉，不是四诊分类。保留教授原始四诊功能，同时增加机器人任务模板，共用底座但隔离数据、标签和模型契约。研究依据与业务未知项见 [需求调研依据](./需求调研依据-四诊与机器人视觉.md)。

本稿保留原始 21 条需求编号。新增要求以 REQ-6.22 等编号表达，非功能要求以 NFR 编号表达。本文规定行为和验收结果；数据库表数、训练并行框架等实现细节由概要设计与详细设计承接。

### 1.1 范围分层

| 层次 | 内容 | 边界 |
| --- | --- | --- |
| 原型基础 | 数据集、图片/XML、分类标注、ResNet 训练、推理、ONNX | 已有相关代码；不等于全部功能实测通过 |
| 首期可信训练闭环 | 未标注图片导入、标签指南、缺失值处理、四人并发保护、数据隔离、版本追溯、可复现训练 | 建议优先实现；不以独立复核为门槛 |
| 首期机器人交付 | 模型输入输出契约、真实样本转换校验、目标设备实测、回滚和回流 | 硬件与接口确认后冻结验收指标 |
| 机器人 P0 | 按钮检测框/类型、RGB-D 配对和定位结果追踪、设备交付 | 根据用户指定方案纳入拟议首期；尚无此实现验收证据 |
| 条件扩展 | 分割、多模态音频/脉搏训练、门/包裹/时序状态、主动学习 | 按实际数据排期；不默认为现有支持 |

分类模型只输出类别或属性，不能直接提供按钮位置、舌体轮廓或机器人运动控制。机器人模板须增加检测训练器和框标注，见 §6.1；分割仍为条件扩展。平台交付感知模型、坐标契约及回放验证，执行轨迹、逆运动学、力控和急停属于机器人控制系统，不纳入本平台训练器。

### 1.2 优先级与确认规则

- **P0**：真实数据训练或交付前必须完成的能力；未完成不得将演示结果标记为正式验收。
- **P1**：首期持续使用需要的效率和治理能力。
- **P2**：后续扩展，条件满足后单独立项。
- 本稿中的优先级、容量、时间与模型指标均为建议；已明确的原始 21 条功能仍保留，不因分期自动删除。
- “待确认”项不视为用户承诺；涉及该项的任务先做接口设计，业务语义确定后再编码。

## 2. 现状核对与必须纠正的假设

以下为 2026-09-07 静态阅读结果，并非本次执行测试所得。旧测试报告仅代表报告所载日期的验证，不能替代新需求验收。

| 编号 | 当前证据 | 对下一版要求的影响 |
| --- | --- | --- |
| GAP-01 | `backend/config/labels.yaml` 为占位标签，四个类别各单选，首项为正常/无 | 应先确认真实任务、属性互斥关系和标签定义，不能把占位配置当专家标准 |
| GAP-02 | `train_service.py::_target_vector` 将缺 XML 或缺失分类头映射为 0；其语义是正常/无 | 未标注、不适用、无法判断不能视为正常；需有效标签掩码 |
| GAP-03 | `train_service.py::_split_train_val` 对图片下标随机划分 | 应按受试者隔离，避免同人、同采集序列或副本跨训练/验证/测试 |
| GAP-04 | `import_service.py::import_zip` 跳过缺少 XML 的图片 | 会阻碍首次人工标注；应支持无 XML 导入并初始化未标注记录 |
| GAP-05 | `dataset_service.py::pull_records` 从目标数据集以外的记录拉取 | 当前“内置库”不等同已接入医院/机器人业务库；需明确真实数据源和源记录 ID |
| GAP-06 | `onnx_service.py::compare` 使用单个随机张量和 CPU Runtime 对比 | 可用于冒烟，不能替代真实数据和目标设备验收 |
| GAP-07 | `train_service.py::_save_checkpoint` 存配置和类别数，但未存完整标签名称映射、数据快照、随机状态或 AMP scaler | 同数量标签改名/换序、数据变化、恢复训练均需版本约束 |
| GAP-08 | `train_service.py::compute_eval` 读取 checkpoint_latest | 评估必须明确绑定权重，正式发布评估应绑定选中的发布候选，不能默认当作 best |
| GAP-09 | v1.0 描述部分删除不删图片；`annotation_service.py::delete_record` 删除图片及 XML | 必须统一产品删除语义与历史数据迁移策略 |
| GAP-10 | `frontend/DESIGN.md` 已定义视觉 token、交互与无障碍约束 | 后续页面遵循既有设计，不另建无关视觉规范；视觉文档中的页面进度需另行实测 |

## 3. 角色与核心业务流程

### 3.1 四人协作与权限

| 角色 | 职责 | 建议权限 |
| --- | --- | --- |
| 平台管理员 | 数据源、用户、资源、备份管理 | 配置及授权；操作留痕 |
| 项目成员（四名使用者按实际分工） | 导入、质检、标注、训练与推理 | 独立账号，记录操作者；不要求提交审核 |
| 标签维护职责 | 维护标签指南和版本、处理歧义 | 可由管理员/成员承担，不设专职专家复核账号 |
| 算法工程师 | 冻结数据、训练、评估、转换 | 读取授权数据、管理实验和候选模型 |
| 机器人集成工程师 | 验证契约、设备测试、部署回滚 | 下载获准模型包、反馈运行结果 |

上述为职责，不要求设置五种独立角色。首期建议仅管理员/成员两级权限，四人各自账号；管理员可兼任成员。共享部署启用身份认证和服务端权限校验，不建设独立标注提交、专家复核或多级审批模块。部署版本仍需有明确发布操作和负责人，但无需多级审批。

### 3.2 标准流程

1. 接入数据，生成稳定样本 ID、来源与文件校验值；缺 XML 不阻断入库。
2. 确认模态与任务，质检合格后标注；不能判断时填写原因。
3. 标签自动保存并校验，满足任务规则后显示已标注；预测建议由成员采纳或修正后成为人工标签，无需另行提交。
4. 生成只读数据版本：四诊按受试者、机器人按场景/面板/采集序列分组并去重后冻结训练、验证、测试清单。
5. 训练前校验有效标签、类别分布与资源；记录完整配置并运行。
6. 用验证集选模型和阈值，用冻结测试集做最终评估，不用测试集反向调参。
7. 转换 ONNX，通过真实样本一致性和机器人设备测试后形成发布包。
8. 机器人返回质量差、低置信度或人工纠正样本，经成员标注进入新版本，不设置专家复核关卡。

## 4. 数据与标签语义

### 4.1 核心实体

| 实体 | 必需信息 | 约束 |
| --- | --- | --- |
| 原始样本 | sample_id、source_id、source_record_id、文件 hash、模态、采集时间、导入时间、device_id | 文件名不是唯一标识；采集时间不得用导入时间无提示替代 |
| 项目与任务模板 | project_id、domain、task_type、schema_version | 四诊/机器人数据隔离；分类/检测选择不同训练器 |
| 机器人采集序列 | scene_id、panel_id、sequence_id、frame_id、时间戳、RGB/depth 配对、标定版本 | 相邻帧和同物理面板关联，不能按帧随机泄漏到测试集 |
| 受试者与采集 | 脱敏 subject_id、session_id、序列/帧关联 | 身份映射单独受控；分组切分使用稳定脱敏 ID |
| 数据集/版本 | dataset_id、version_id、样本清单、标注版本、切分清单、创建人/时间 | 修改数据集不改变已冻结版本 |
| 标签体系 | taxonomy_version、task_id、属性 ID、标签 ID/名称/定义、互斥与适用规则 | ID 稳定，名称与显示顺序不决定训练编码 |
| 标注修订 | annotation_id、revision、有效值/未知状态、来源、操作者、质量、完整性状态 | 模型置信度不等于人工正确概率 |
| 训练任务 | run_id、版本、配置、环境、状态、日志、checkpoint | 所有指标绑定具体权重与数据版本 |
| 模型版本 | model_id、权重 hash、标签映射、输入输出契约、评估/转换/设备报告 | 禁止同名文件替换后仍保留旧的通过状态 |
| 发布与回流 | release_id、device_id、模型版本、来源样本、反馈原因、处理状态 | 可追溯、可撤回，不自动更新机器人模型 |

### 4.2 分类与多模态规则（P0）

- REQ-DATA-01：明确区分**模态**（舌图、面图、脉搏波形、音频）与**预测属性**（例如舌色、苔色、苔厚）。研究支持同一舌图多个属性共存；各属性内部是否互斥由标签指南定义，依据见《需求调研依据-四诊与机器人视觉.md》§3。
- REQ-DATA-02：每个属性分别声明单选、多选或数值型。单选可以使用 softmax；多选不得强行单选，需独立阈值及兼容的损失。数值型作为条件扩展另行设计。
- REQ-DATA-03：正常、未标注、无法判断、不适用分别编码。只有明确人工标注的正常值才计入正常类；缺失值不参与对应任务的损失与指标分母。
- REQ-DATA-04：单张舌图不得默认作为脉象或声音的有效监督。多模态任务须定义输入模态、样本配对、时间同步和缺模态策略。
- REQ-DATA-05：真实标签字典须包含定义、正反例、边界例、互斥关系、适用模态和维护人；由业务负责人确认后冻结版本。示例标签仅用于讨论。

验收：构造“明确正常、未标注、无法判断、不适用”四类样本，核对训练有效计数；未观察标签对相应损失与评价计数无贡献。一个同时具有两种非互斥属性的样本可完整保存、训练、推理及往返导出。

### 4.3 XML 与历史兼容（P0）

- XML 继续作为原始 6.4/6.18 的兼容交付格式；旧 schema 见 `annotation-schema.md`。
- 新版应携带 schema_version、sample_id、taxonomy_version、任务/属性标签及状态、标注来源与修订 ID；修订与审计可关联独立清单，存储设计须规定唯一权威来源与索引同步机制。
- 旧 XML 缺少标签只能解释为未知，不能补成正常；旧 confidence=1.0 不能单独证明人工复核通过。
- 旧格式不能表示的多选、框或掩码不得静默截断；应拒绝有损导出并说明原因，或提供经用户选择的受限兼容导出。
- 保留导入原文件和迁移报告。未修改的原文件可校验字节一致；修改/升级后的 XML 验证语义一致，不要求与旧格式逐字节相同。
- XML 更新与数据库镜像失败时应可重试和对账；原子文件替换不等同并发编辑冲突已解决。

### 5.1 导入和质量过滤的补充约定

- “过滤质量合格”存在歧义，待 DEC-03 确认；界面应采用“仅合格 / 仅不合格 / 未质检 / 全部”等明确选项，不使用孤立的“过滤”开关。
- 训练默认只使用质量合格、对应任务标签有效且没有未解决编辑冲突的样本，**不要求提交或专家复核**。允许部分属性缺失时按有效掩码计数；纯预标注未经成员采纳不自动视为人工真值。质量筛选默认值仍是工程建议，待 DEC-03 明确原意。
- 原始 GIF 默认仅按静态图任务处理；建议读取首帧并标记转换记录，保留原文件。动态帧训练作为扩展，不静默当成已支持视频。
- 时间统一持久化为 UTC、界面显示指定时区；新增接口建议采用 `[开始, 结束)`，历史闭区间 API 须通过版本区分迁移。缺失采集时间单独筛选，文件修改时间只作带来源标记的回退值。
- 相同内容重复导入默认复用资产并返回重复统计；同名不同内容不得直接覆盖。图片与 XML 配对存在歧义必须列入待处理清单。

## 7. 任务状态与数据保护规则

- 导入/导出/推理/转换任务统一具有 queued、running、succeeded、failed、cancelled；部分成功用独立计数和明确状态说明，不冒充全部成功。
- 训练任务增加 stopping、interrupted；服务重启后将残留 running 识别为 interrupted，显示可恢复 checkpoint，不能永久显示运行中。
- 保存、生成数据版本、发布必须有服务器成功回执。前端乐观状态不能代替持久化成功；首期无提交复核操作。
- 并发修改使用 revision 校验；冲突提示差异、保留用户草稿，由用户选择合并或重试，不静默后写覆盖。
- 首期建议采用回收站，保留期由管理员配置；只有确认无数据版本/实验引用的资产才允许物理清除。实际个人数据删除申请走受控清除流程，并标记受影响历史版本不可完整复现。
- 标注修改日志保存前后修订、操作者、时间和原因；禁止只记录“已修改”而不能追查实际变化。

| 必须冻结的项目 | 当前状态 | 验收证据 |
| --- | --- | --- |
| 任务与目标类别/属性 | 方案已指向按钮检测+RGB-D定位；类型、编号/状态属性待样本冻结 | 标签字典与输入样例 |

## 10. 分期与验收计划

### 10.1 建议实施顺序

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| A：冻结业务语义 | 四人免审核流程；四诊/机器人模板、标签草案、数据源、设备契约 | DEC-04已确定；其他业务未知项明确记录，先完成不依赖未知项的接口 |
| B：可信数据闭环 | 无 XML 导入、缺失掩码、质检、四人并发、去重、分组切分、版本；机器人框标注/RGB-D导入 | 数据验收场景通过，缺失不伪造正常，纯图与RGB-D能力区分 |
| C：可复现训练 | 分类及按钮检测训练器、任务持久化、模型元数据、恢复训练、best 绑定评估 | 两种任务闭环分别通过；多卡/FP16 分别有证据 |
| D：设备交付 | ONNX 真实样本校验、部署包、目标设备测试、批准/回滚 | 第 9 节门槛全部冻结且测试通过 |
| E：持续打磨 | 多人效率、实验比较、难例回流、主动学习与门/包裹任务 | 按人力/数据量确认收益后分批验收；不默认增加审核流程 |

视觉优化可随各阶段进行，优先保证标注保存状态、任务错误反馈和数据筛选体验。工期与预算需要团队投入信息后估算，不以“已有网站”推断剩余工作量很小。
